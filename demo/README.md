# Shiori デモ用データセット

社内ナレッジRAG「Shiori」の検索精度デモおよび評価のためのデータ一式です。架空の医療機関を題材にした社内文書6本と、30問の評価質問セットで構成されます。

## ⚠️ 架空データについて

**このフォルダの内容はすべて創作です。**

- 「さくら総合病院」は実在しません。実在の医療機関・企業・団体・個人とは一切関係がありません。
- 記載の内線番号、PHS番号、様式番号、文書番号、制定日、改訂日はすべて創作です。
- 実在の患者情報は含まれません。実在企業の規程を引用・改変したものではありません。
- 医療系文書は**運用ルール・手続き・組織体制のみ**を扱い、臨床判断の基準、薬剤名および投与量は一切記載していません。**実際の臨床業務に用いてはなりません。**
- 各文書の冒頭にも同趣旨の注記を記載しています。

### 固有名詞の扱い

| 名称               | 位置づけ                                                                   |
| ------------------ | -------------------------------------------------------------------------- |
| さくら総合病院     | 架空の医療機関（345床・二次救急）。6文書すべての発行元となるデモ用テナント |
| 株式会社みなと商事 | 架空の企業。旅費規程 第6条で「指定旅行代理店」として登場する取引先         |

デモの主体を1組織に統一するため、6文書はすべてさくら総合病院の文書としています。株式会社みなと商事は取引先として登場させることで、社外の固有名詞が混在するケースも同時に再現しています。

なお、01〜03（就業規則・旅費規程・育児介護休業規程）は業種を問わない汎用的な内容であり、医療業界以外の商談ではそのまま一般企業のサンプルとして提示できます。医療色を出したい場合のみ04〜06を追加してください。

### 書式について

チャンク分割（`src/lib/chunking.ts`）の見出し検出をひととおり通すため、意図的に2種類の書式を混在させています。

- **01〜03（規程類）**: `第N章` / `第N条` の日本語見出し行のみで構成
- **04〜06（マニュアル類）**: markdown の `## 1.` / `### 1.1` 見出しで構成

いずれの文書も、`（1）（2）` の列挙は見出しに誤検出されないよう本文として扱われ、全チャンクが 700 トークン以内に収まることを実装で確認済みです。生成される `heading_path` は `01_就業規則 > 第4章 休暇 > 第22条 年次有給休暇` のような形になります。

## 5分デモ台本

商談やポートフォリオ紹介で、そのまま上から順に実行できる構成です。所要5分。

### ① 文書を取り込み、チャンク分割を見せる（40秒）

`01_就業規則.md` をアップロードする。取り込み後、チャンク一覧を開き、`第4章 休暇 > 第22条 年次有給休暇` という **heading_path が保持されている**ことを見せる。

> 「単に1,000文字ずつ機械的に切っているのではなく、章立てを理解して切っています。だから引用が『就業規則の第22条』まで出せます。」

### ② 看板質問に、出典付きで答える（60秒）

チャットに **「有給の繰り越しは何日まで？」** と入力する。

見せるポイントは3つ。

- **回答**: 「翌年度に繰り越せる期間は2年間、繰越分を含めて40日が上限」
- **出典**: 就業規則 第4章 休暇 第22条（クリックで該当箇所へジャンプ）
- **表記ゆれ**: 質問は「有給」、文書の表記は「年次有給休暇」。それでも当たる

続けて **「有休っていつまで持ち越せる？」**（評価セット B-01）と口語で聞き直し、同じ答えが返ることを見せる。キーワード検索だけでは当たらない質問である点を補足する。

### ③ 答えられない質問に、正直に答えを保留する（50秒）

**「職員駐車場の月額利用料はいくらですか？」**（評価セット D-01）と入力する。

「該当する記載が見つかりませんでした」と返る。ここが最大の見せ場になる。

> 「旅費規程に『駐車料金』という語はあるので、検索自体は近い文を拾ってきます。それでも答えを作りません。社内向けAIで一番怖いのは、それらしい嘘を自信満々に返すことなので、閾値を下回ったら答えを出さない設計にしています。」

### ④ 管理画面の未回答キューに、いま溜まったことを見せる（40秒）

管理画面の「未回答の質問」を開く。いま投げた駐車場の質問が、日時と質問件数つきで記録されている。

> 「答えられなかった質問は捨てずに溜まります。ここが、社内の“よくある質問だが文書化されていないこと”のリストになります。」

### ⑤ その場でFAQを登録する（40秒）

未回答キューの行から「FAQとして登録」を開き、回答を入力して保存する。

- 質問: 職員駐車場の月額利用料はいくらですか？
- 回答: 職員駐車場の利用料は月額3,000円です。給与から控除されます。申込みは事務部総務課（内線3100）で受け付けます。

（この回答内容も架空の設定です）

### ⑥ 同じ質問が、今度は即答される（30秒）

チャットに戻り、**もう一度「職員駐車場の月額利用料はいくらですか？」** と入力する。今度は登録したFAQがそのまま返る。生成を経由しないため応答が明らかに速いことも指摘する。

> 「使われるほど賢くなる、と言葉で言うだけでなく、いまこの場で1周回しました。運用担当者の作業は、溜まった質問に答えを書くだけです。」

### ⑦ 利用ログとコストを見せる（40秒）

管理画面の利用状況を開き、質問件数、回答率、平均応答時間、推定APIコストを見せる。

> 「1問あたりのコストが見えるので、導入したあと『いくらかかっているのか分からない』状態になりません。」

### 台本を実行する前の準備

- 6文書を取り込み済みにしておく（②の直前に①でアップロードするのは `01_就業規則.md` のみ、または再取り込みのデモとする）
- ⑤で登録するFAQを、デモ前にいったん削除しておく
- 放射線科ユーザーと看護部ユーザーの2アカウントを用意しておく（RLSデモを追加する場合）
- 未回答キューを空にしておく（④で新規の1件だけが見えるほうが分かりやすい）

## 評価質問セット

| ファイル              | 用途                               |
| --------------------- | ---------------------------------- |
| `eval/questions.md`   | 人が読む一覧表。手動確認用         |
| `eval/questions.json` | スクリプトで一括評価する機械可読版 |

30問の内訳は次のとおりです。

| カテゴリ | 問数 | 内容                           | 見たいこと                                         |
| -------- | ---- | ------------------------------ | -------------------------------------------------- |
| A        | 15   | 単一文書で明確に答えられる質問 | 基本的な検索精度と、条・節レベルまでの出典表示     |
| B        | 8    | 表記ゆれ・言い換え・口語を含む | ベクトル検索とキーワード検索のどちらが効いているか |
| C        | 4    | 複数文書をまたぐ質問           | 複数チャンクを統合して答えられるか                 |
| D        | 3    | 答えられないべき質問           | 捏造せず答えを保留し、未回答キューに記録できるか   |

### 使い方

**手動で確認する場合**は `eval/questions.md` の表を上から順に投げ、「回答に含むべき語」がすべて含まれているかを確認します。

**スクリプトで評価する場合**は `eval/questions.json` を読み込み、次の条件で採点します。

```
A・B・C（should_answer: true）
  1. 上位の出典に expected_document が含まれる
  2. 出典の heading_path が expected_heading で終わる
  3. 回答本文が expected_answer_contains の全要素を含む

D（should_answer: false）
  回答を生成せず、unanswered に記録される
```

目安は、検索ヒット率90%以上／見出し一致率80%以上／回答正答率85%以上、**D区分の誤回答率は0%**です。D区分だけは他の指標より優先します。答えられないことを答えられる、という点がこの製品の中心にあたるためです。

### 検証済みの対応関係

`expected_answer_contains` に記載した文字列は、対応する文書本文に実在することを全問確認済みです（カテゴリCは `expected_document` と `supporting_documents` の和集合に対して確認）。`expected_heading` も、実際の `chunkDocument()` が生成する `heading_path` と後方一致することを確認しています。

**文書を改訂したときは、この対応関係を必ず取り直してください。**ここがずれると評価そのものが成立しません。
