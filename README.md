# Shiori — 社内ナレッジ検索アシスタント

社内規程やマニュアルをアップロードすると、**どの文書のどの条文を根拠にしたかを示しながら**質問に答えるRAGアプリケーションです。
根拠が見つからないときは推測せず「該当する記載が見つかりませんでした」と答え、その質問を管理画面の改善キューに積みます。

> ポートフォリオ作品です。デモデータは架空の医療機関のものを使用しています（`demo/README.md` 参照）。

---

## この作品で見てほしいところ

社内チャットボットは作れる人が多い領域です。差がつくのは「作ったあと運用できるか」なので、次の3点に力を入れています。

### 1. 答えられないときに、答えない

RAGで一番困るのは、根拠がないのに自信ありげな答えが返ることです。
本作は判定を2段に分けています。

1. 検索結果の cosine 類似度が閾値（0.35）を下回れば、**生成せずに**拒否する
2. 閾値を超えた場合も、生成モデルにまず「この資料で答えられるか」を1行で宣言させ、`NO_EVIDENCE` なら本文を作らせずに拒否する

**なぜ2段なのか**を実測で決めています。デモ30問で測ったところ、答えるべきでない質問の類似度は 0.502／0.544／0.580 で、答えるべき質問の下位8問（0.419〜0.578）と完全に重なっていました。どこに線を引いても誤答と正答が同じだけ消えます。埋め込みが測るのは「話題の近さ」であって「答えが書いてあるか」ではないためです。

| 判定方式                                  | 誤答（答えるべきでないのに答えた） | 誤拒否（答えるべきなのに拒否した） |
| ----------------------------------------- | ---------------------------------- | ---------------------------------- |
| cosine 閾値のみ                           | **3 / 3**                          | 0 / 27                             |
| cosine 閾値 ＋ 根拠判定                   | **0 / 3**                          | 2 / 27                             |
| cosine 閾値 ＋ 根拠判定 ＋ 質問の書き換え | **0 / 3**                          | **0 / 27**                         |

`npm run eval:refusal` で再現できます。

2段目を入れた時点で残っていた誤拒否2問は、モデルの判断ミスではなく**検索が根拠を渡せていなかった**もので、モデルは「渡された資料からは答えが導けない」と正しく言っていました。そちらは検索の手前で質問を整えて解いています（[後述](#残った誤拒否2件は閾値ではなく聞き方の問題だった)）。

### 2. 精度を上げる作業が、管理画面で完結する

答えられなかった質問は `unanswered` キューに自動で積まれます。管理者がそこに回答を書くと `faq_overrides` に登録され、**次から同じ質問が即答になります**。
「AIの精度が悪い」という漠然とした不満を、「この質問に答えられていない → ここに回答を足す」という具体的な運用作業に変換することを狙っています。

### 3. 誰が何を見られるかがDBで担保されている

部署限定の文書（例：放射線部門マニュアル）は、他部署のユーザーが検索しても**検索結果の時点で出てきません**。
アプリ側で絞り込みを書き忘れても漏れないよう、検索関数 `hybrid_search()` を `security invoker` にして、呼び出したユーザーのRLSをそのまま効かせています。

これも実測しています（`npm run eval:rls`）。同じ質問 A-14 を3アカウントで投げ分けた結果です。

| ログイン         | 見える文書 | 検索の出典に 06 が混ざるか | 最終的に |
| ---------------- | ---------- | -------------------------- | -------- |
| 放射線科スタッフ | 6件        | 混ざる                     | 回答     |
| 看護部スタッフ   | **5件**    | **混ざらない**             | **拒否** |
| 管理者           | 6件        | 混ざる（`is_admin()`）     | 回答     |

看護部側で効いている仕組みは2つあり、順番に働いています。まず RLS が `06` を**検索結果に入る前に**落とし、そのうえで残った `05_医療安全管理指針` は閾値 0.35 を超えて生成まで進みますが、2段目の根拠判定が「この資料では答えられない」と拒否します。**アクセス制御と拒否ロジックが別々の層で噛み合っている**ことまで確認できます。

### 検索・生成

```
質問
 │
 ├─▶ Embedding 化
 │
 ├─▶ ① FAQ照合          cosine ≧ 0.92 ─▶ 即答（生成をスキップ）
 │
 ├─▶ ② 質問の書き換え    Claude Haiku 4.5
 │      「有休っていつまで持ち越せる？」

 │        → 年次有給休暇 繰り越し 期限

 │
 ├─▶ ③ ハイブリッド検索  hybrid_search() を検索文の本数だけ並列に
 │      ├ ベクトル検索   pgvector cosine         上位20件
 │      └ キーワード検索 pg_trgm word_similarity 上位20件
 │                     └─▶ RRF で統合 ─▶ 各5件
 │                          └─▶ 検索文が複数なら、結果同士をさらに RRF ─▶ 上位8件
 │
 ├─▶ ④ 判定1（無料）     cosine < 0.35 ─▶ 拒否 ＋ unanswered へ記録
 │
 └─▶ ⑤ 生成             Claude Sonnet 4.6
        ├ 1行目に根拠の有無を宣言させる
        │   NO_EVIDENCE ─▶ 判定2で拒否 ＋ unanswered へ記録
        └ ANSWERABLE   ─▶ 2行目以降が回答本文（出典 [1][2] を強制）
                         │
                         └─▶ NDJSON でストリーミング
                              meta / citations / text… / done
```

出典（citations）は1行目の判定を読んでから送ります。先に送ると、拒否したのに根拠だけが並ぶ画面になるためです。

②で Haiku を1回呼びますが、①の FAQ に当たった質問では呼びません。書き換えに失敗しても例外にはせず、元の質問だけで検索を続けます（壊れたときに以前の挙動へ戻るだけにしてあります）。

## 設計上の判断と、その理由

実装中に踏んだ問題と対処を残しておきます。この作品で一番説明したい部分です。

### 日本語のキーワード検索に `tsvector` を使っていない理由

PostgreSQL 標準の `to_tsvector` は空白区切りで語を切るため、分かち書きしない日本語では機能しません。形態素解析拡張（pgroonga / textsearch_ja）は Supabase では利用できません。
そこで **pg_trgm の `word_similarity`**（文字3-gramの一致度）でキーワード側の順位を作っています。

### 「ハイブリッド検索」が実はベクトル検索だけだった

評価スクリプトを回したとき、**ベクトル検索のみとハイブリッドの数字が小数点以下まで完全に一致**しました（Hit@1 88.9% / MRR 0.944、順位が変わった質問0問）。偶然にしては出来すぎているので `hybrid_search()` の戻り値を1件ずつ見たところ、27問すべてで `lexical_rank = null` でした。キーワード側が一度も発火しておらず、RRF はベクトル順位だけを足していたことになります。

原因は `%>` 演算子が見る `pg_trgm.word_similarity_threshold` の既定値 0.6 でした。pg_trgm は英数字以外を語の区切りとして扱うので、分かち書きしない日本語では**質問文がまるごと1語**になります。n文字の語のトライグラムは n+1 個で、`word_similarity` はおおむね「一致した数 ÷ 質問側の数」です。「有休っていつまで持ち越せる？」は13文字＝14トライグラムなので、0.6 を超えるには14個中9個、つまり質問文がほぼそのまま本文に書かれている必要があります。起こりえません。

英語なら語ごとに区切られるので 0.6 は妥当な既定値です。**日本語ではこの前提が崩れる**、というのが見落としでした。

なお Supabase の `postgres` ロールは superuser ではないため、関数定義に `set pg_trgm.word_similarity_threshold = '0.2'` を付ける方法は `ERROR: 42501: permission denied to set parameter` で通りません。`%>` をやめて `word_similarity(...) >= しきい値` を直接書いています（`0004_lexical_threshold.sql`）。

同じ失敗を繰り返さないよう、`npm run eval` はキーワード側が何問で発火したかを常に表示し、0件なら警告を出します。

```
キーワード側が1件以上ヒットした質問: 0/27
  ⚠ 0件です。RRFがベクトル順位しか見ていない＝実質ベクトル検索のみになっています。
```

### しきい値を下げすぎて、今度は正解が押し出された

しきい値 0.2 で直したところ、キーワード側は 0/27 → 9/27 で発火するようになりました。Hit@1 も MRR も動きません。直ったように見えます。
ところが `npm run eval:refusal` を回すと、**それまで答えられていた A-13 が拒否に転落**していました。

`npm run inspect` で中を見ると、答えが載っている「4. 患者影響度分類」（cosine 0.489・ベクトル3位）が融合5位から7位に落ち、代わりに**ベクトル上位20件にすら入っていない**「1. 基本理念と目的」（cosine 0.000）がキーワード1位として6位に入り込んでいました。

30問すべてについて全チャンクとの `word_similarity` を実測すると、理由がはっきりします。

| 質問     | 最大値       | 0.2以上の件数 |
| -------- | ------------ | ------------- |
| A-11     | 0.407        | 3             |
| A-03     | 0.357        | 2             |
| A-14     | 0.300        | 1             |
| **A-13** | **0.241**    | **7**         |
| B-01〜08 | 0.059〜0.143 | 0             |

A-13 は最大でも 0.241 なのに 0.2 以上が7件あります。**弱い一致が横一線に並んだ「ノイズの平地」**で、その中の1位は実質ランダムに決まります。

ここで私が最初に書いていた「RRF は順位しか使わないので、しきい値を下げても上位に食い込まない限り影響しない」という理屈は**誤りでした**。全部がノイズのときはノイズが1位になり、RRF は1位に `1/(60+1)` をそのまま与えます。本物の1位と同じ重みです。

ノイズ（≤0.241）と本物の一致（0.300〜）の間が空いていたので、その谷に **0.3** を置きました。A-13 は回答に戻り、誤拒否は 3/27 → 2/27 に戻っています。

### キーワード検索は「言い換え」には効かない

上の表でもう一つ効いたのが、**B（表記ゆれ・言い換え）が 0.059〜0.143 と全カテゴリ最低**だったことです。キーワード側を足した狙いはまさにこのカテゴリだったので、これは想定と逆でした。

理由は考えれば当然で、pg_trgm が見ているのは**文字面の重なり**、言い換えは**文字面が最も重ならない場合**だからです。B-01 は「有休…持ち越せる」、規程側は「年次有給休暇…繰り越し」で、共通するトライグラムがありません。しきい値をいくら下げても拾えません。**同義語はベクトル側の担当**であって、トライグラム側の担当ではありませんでした。

逆にキーワード側が本来効くのは、埋め込みが潰しがちな**そのままの珍しい文字列**（型番・薬剤名・「第22条」のような条番号・ID）です。いまの評価セットにはそれがほとんど無いため、**このデモ規模ではキーワード側は保険として積んである状態**です。実測でそう言える、というところまでが今回の結論です。

### 残った誤拒否2件は、閾値ではなく「聞き方」の問題だった

しきい値も検索方式も詰めたうえで、まだ2問が答えられていませんでした。どちらも**根拠は文書にあるのに拒否している**、いちばん困る種類の失敗です。

原因を分けて考えるために、評価セットの中の自然な対照実験を使いました。

| 質問                                          | 言い方   | cosine | 順位        |
| --------------------------------------------- | -------- | ------ | ----------- |
| A-01 有給休暇の繰り越しは何日までできますか？ | 正式名称 | 0.661  | **1位**     |
| B-01 有休っていつまで持ち越せる？             | 口語     | 0.461  | 2位（拒否） |

**答えも参照先の条文も同じで、違うのは言い回しだけ**です。つまりインデックスの問題でもしきい値の問題でもなく、13文字の口語だと埋め込みが「休暇一般」としか捉えられない、という語彙の問題でした。前節のとおりキーワード側でも拾えません（共通するトライグラムが無い）。

もう1問の C-04「3歳の子どもを育てている職員は、1日の勤務時間が通常より何時間短くなるか」は種類が違い、上位8件すべてが育児介護休業規程で埋まっていました。短縮後の6時間は取れるのに、差を出すのに必要な「通常＝8時間」（就業規則 第12条）が入りません。**1問に対して調べ物が2つ必要なのに、検索を1回しか投げていなかった**わけです。

どちらも検索の手前で質問を整えれば解ける話なので、Haiku で**検索文への書き換え**を挟みました（`src/lib/query-rewrite.ts`）。

```
有休っていつまで持ち越せる？
  → 年次有給休暇 繰り越し 期限

3歳の子どもを育てている職員は、1日の勤務時間が通常より何時間短くなりますか？
  → 育児短時間勤務 勤務時間 短縮
  → 所定労働時間            ← 比較の基準になる「通常」を別に引く
```

結果（27問、`npm run eval`）:

|                  | Hit@1     | Hit@3 | MRR       |
| ---------------- | --------- | ----- | --------- |
| ベクトル検索のみ | 88.9%     | 100%  | 0.944     |
| ハイブリッド+RRF | 88.9%     | 100%  | 0.944     |
| ＋質問の書き換え | **92.6%** | 100%  | **0.963** |

効いたのは狙ったカテゴリだけで、B（表記ゆれ・言い換え）が Hit@1 75.0% → **87.5%**、MRR 0.875 → 0.938。A と C の順位は動いていません。複数文書が必要な質問で必要な文書がすべて揃った割合は 3/4 → **4/4**、生成まで通した誤拒否は 2/27 → **0/27**（誤答は 0/3 のまま）になりました。

書き換えは1問あたり数十トークンなので $0.001 未満です。

#### 書き換えで踏んだ失敗2つ

**1. 書き換えを「置き換え」にしていた。** 最初の実装では元の質問を捨てて書き換え後の文だけで引いていて、Hit@1 が **88.9% → 85.2%**（MRR 0.920）と下がりました。A-06「出張から戻ったあと、旅費の精算はいつまでに提出しますか？」は元のままなら1位、「旅費精算 提出期限」では2位。他に B-06 と B-08 も落ちました。

書き換えは取りこぼしを**足す**ためのもので、元の言い回しで既に1位を取れているものを捨てる理由はどこにもありません。**元の質問を必ず1本目の検索文として残す**ようにしたところ、順位が下がった質問は0問になりました。上の 92.6% はこの形での数字です。

**2. 前処理モデルが質問に答えようとした。** C-02 と D-03 で、Haiku が検索文の代わりに「お答えできません。この質問は規程ではなく契約書に…」という断り文を返してきました。それがそのまま埋め込まれ、意味のない照会が1回増えていました。プロンプトで禁止しても再発したので、**形の側でも弾いています**。検索文は助詞を落とした語の並びなので短く、実測の最長は20字、断り文は100字超でした。40字を超える行と句点で終わる行を捨てる、という切り方で分離できます。

なお「分けすぎ」は指示では直りませんでした（27問中15問が3本、「賞与 支給時期／賞与 支給日」のような言い換えだけの2行目を出し続ける）。ただし実測では順位が下がった質問は0問、増えた費用も埋め込み1回ぶんで、実害は遅さだけでした。そこで検索文の指示を足すのはやめて、**検索を並列化**しました。所要時間は最も遅い1本と同じになり、本数にほぼ依存しません。

### 評価スクリプトが、本番とは違う経路を測っていた

書き換えを入れたあとも `npm run eval:refusal` は「B-01 は誤拒否」と報告し続けていました。ところが `npm run eval` 側では B-01 の cosine が 0.583 まで上がっている。**同じ質問に2つの数字が出ている**のはおかしい、というところから見つかった不具合です。

原因は、`eval-refusal.mts` が `retrieve()` を呼ばず、検索の手順を自前で書き写していたことでした。書き写した側は書き換えを知らないので、いつまでも古い経路を測っていたわけです。

なぜ写しがあったかというと、`rag.ts` が `./embedding` のような**拡張子なしの相対 import** を持っていて、Node の型ストリッピング（`--experimental-strip-types`）ではこれを解決できず、スクリプトから読めなかったからです。`.ts` を明示する（`allowImportingTsExtensions`）だけで読めるようになったので、評価は本番の `retrieve()` を直接呼ぶ形に統一しました。

数字が緑になっただけで安心しないための教訓として、そのまま残しています。**評価が本番と違う経路を通っているなら、それは測っていないのと同じです。**

### RRFスコアで「答えられるか」を判定してはいけない

RRFの統合スコアは `1/(k+rank)` の和で、**順位だけ**から決まります。つまり上位1件のスコアは、中身が的外れでも `≒0.0328` に張り付きます。
これを閾値判定に使うと、無関係な質問にも自信満々で答えてしまいます。

そのため `hybrid_search()` は、並べ替え用の `score`（RRF）と判定用の `vector_similarity`（cosine）を**別々に返します**。SQL側にもコメントで明記してあります。

```sql
comment on function public.hybrid_search is
  'RRF統合スコア(score)は順位のみに基づくため、関連度の絶対評価には使えない。
   「答えられるか」の判定には必ず vector_similarity（cosine類似度）を使うこと。';
```

### チャンク分割で本文が見出しに化ける問題

素朴な見出し判定を書いたところ、就業規則の

```
1. 病院は、採用の日から6か月間継続して勤務し…年次有給休暇を付与する。
```

という**本文**が「番号付き見出し」と誤認され、`第4章 休暇 > 第22条 年次有給休暇` の階層を巻き戻して本文が `heading_path` に入っていました。看板デモの質問がそのまま壊れる不具合です。

3点で対処しました。

1. 見出し種別ごとに最大文字数を設ける（番号付きは30字まで）
2. 行末が句読点（`。．、，;`）なら見出しではないと判定する
3. `（1）（2）` の列挙は見出しにせず、親の条文に属させる

デモ文書6本（180チャンク）で `heading_path` の欠落0件・700トークン超過0件を確認済みです。

### service role キーの使用範囲を4つに閉じている

管理画面の一覧・集計を service role（RLSバイパス）で実装すると楽ですが、キーが漏れたときの影響範囲を説明できなくなります。
`conversations` / `messages` / `citations` / `feedback` に管理者向けの**閲覧専用**ポリシー（`*_admin_read`）を用意し、管理画面もログインユーザーの権限で読んでいます。管理者でも他人の会話は書き換えられません。

service role を使うのは次の4つだけです。

1. 取り込みワーカー（チャンク投入・ステータス更新）
2. 監査ログの書き込み（利用者本人には書かせない）
3. 未回答キューへの記録（`unanswered` は管理者しか触れないポリシーのため）
4. `auth.users` の参照（メールアドレスはRLS越しには読めない）

### RLS判定を JWT ではなく関数に寄せている

`auth.jwt()->>'org_id'` を直接見る方式はカスタムクレームの設定に依存し、ポリシー同士が再帰参照して無限ループになりがちです。
`profiles` を引く `security definer` 関数（`current_org_id()` / `current_department()` / `is_admin()`）に判定を集約しています。

### 公開デモの回数制限を、消せないテーブルで数えている

このデモはログインボタンにパスワードを埋めてあります。`NEXT_PUBLIC_*` は**ビルド時にクライアントのJSへ静的置換される**ので、公開した時点でパスワードは誰でも取り出せます。「ログインできる人しか使えない」は防御になっていません。

実際に効いているのは1日あたりの回数制限だけです。1問の内訳を実測すると（3問平均・入力2,203 / 出力366トークン）、

| 内訳           | 1問あたり    |
| -------------- | ------------ |
| Sonnet 生成    | $0.0121      |
| Haiku 書き換え | $0.0012      |
| Embedding      | $0.00001未満 |
| **合計**       | **$0.0133**  |

上限30問なら、毎日使い切られても $0.40/日・$12/月です。

最初は `messages` の件数を数えるつもりでしたが、`messages_own` ポリシーが `for all` なので**ユーザーは自分の messages を DELETE できます**。件数を上限判定に使うと、消せば枠が戻る。そこで RLS を有効にして**ポリシーを1つも作らない**テーブルを別に持ち、`security definer` 関数だけが触れるようにしています。

上限値は関数の引数にしていません。引数にすると、クライアントが anon キーで直接RPCを叩くときに好きな上限を渡せます。関数は「数えて返す」だけで、通す/断るの判断はサーバ側が環境変数と突き合わせて行います。

`npm run eval:quota` で、増えること・ユーザーから消せないこと・ユーザーごとに独立していることを実測できます。

```
○ 呼ぶたびに1つ増える            1回目 1 → 2回目 2
○ ユーザーからカウンタを消せない  削除後の値: 3（戻っていない）
○ ユーザーごとに独立して数える    nurse: 4 / rt: 1
○ 上限との突き合わせ              used=4 ≤ limit=30 → 通す
```

2行目は「削除がエラーになるか」ではなく「値が戻ったか」で判定しています。PostgREST はポリシーが無いテーブルへの DELETE を「該当0件」として正常終了させるため、エラーの有無だけを見ると消せたと誤読します。

### 精度の測り方

デモ文書を取り込んだあと、次のコマンドで30問を投げて検索精度を測れます。

```bash
npm run eval
```

**ベクトル検索のみ** / **ハイブリッド+RRF** / **＋質問の書き換え** の3通りで Hit@1 / Hit@3 / Hit@5 / MRR を並べて出します。
「その工夫に意味があったか」を毎回数字で言えるようにするためのもので、**順位が下がった質問は個別に列挙します**（工夫を足すときに一番見たいのは平均ではなく、それで壊れたものです）。
生成は行わないので、費用は Embedding と書き換えの Haiku で1回 $0.02 程度です。

```bash
npm run eval:refusal   # 根拠判定まで通す。生成を伴うので $0.3 前後かかる
npm run eval:rls       # 部署フィルタ（RLS）が効いているかを3アカウントで検証
npm run eval:quota     # 公開デモの回数制限が消せない形で効いているかを検証
npm run inspect -- "有休っていつまで持ち越せる？"   # 1問だけ、何が引けたかを見る
```

`eval:refusal` は「誤答0件」を守れているかの確認用で、本番の `retrieve()` をそのまま呼びます（検索の手順を書き写していたせいで古い経路を測っていた時期があります。[後述](#評価スクリプトが本番とは違う経路を測っていた)）。答えが変なときに原因が検索なのか生成なのかを切り分けるには `inspect` を使います。

`eval:rls` と `eval:quota` は毛色が違い、**他の3つが測れないもの**を測ります。`eval` も `eval:refusal` も service role で動くので RLS を素通りしており、部署フィルタについても回数制限についても何も言えません。この2つは Admin API でデモユーザーのセッションを発行し（パスワードはリポジトリに置きません）、**実際のユーザーのJWTで**境界そのものを突きます。

#### Hit@k を信じすぎない

Hit@k は正解文書が1本でも上位に入れば当たりと数えます。**2文書を突き合わせないと答えられない質問では、片方しか引けていなくても満点に見えます。**

実際 C-04「3歳の子を育てている職員は勤務時間が通常より何時間短くなるか」は Hit@1 が当たりでした。しかし上位5件はすべて育児介護休業規程（短縮後＝6時間）で、差を出すのに必要な就業規則第12条（通常＝8時間）は20件のプールの16位に沈んでいました。Hit@1 100% なのに答えは作れません。

そこで `npm run eval` は「必要な文書がすべて上位に入った割合」も出すようにしました。

```
複数文書が必要な質問で、必要な文書がすべて揃った割合
  書き換えなし: 3/4      ← C-04 は片方の文書しか引けていない（＝完答できない）
  書き換えあり: 4/4
```

この取りこぼしは埋め込みの引き方を変えても直りませんでした（上位20件まで見ても16位）。**1回の検索で完結する設計そのものが原因**で、「通常の所定労働時間は何時間か」を別の検索として投げ直す必要があったからです。これは[質問の書き換え](#残った誤拒否2件は閾値ではなく聞き方の問題だった)で解いています。

この指標を足していなければ、C-04 は Hit@1 100% の「解けている質問」に見えたままでした。**平均だけを見ていると、直すべきものが見えません。**
