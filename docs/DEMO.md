# デモ環境の作り方

まっさらな Supabase プロジェクトから、デモ文書6本を取り込んで
`npm run eval` が通るところまでの手順です。所要 20〜30分（大半は取り込み待ち）。

前提として `docs/SETUP.md` の 1〜4（プロジェクト作成・マイグレーション実行・
Storage バケット作成・`.env.local`）が終わっていること。

商談で見せるときの進行台本は `demo/README.md` の「5分デモ台本」にあります。
こちらは**その台本を実行できる状態を作るまで**を扱います。

---

## 1. マイグレーションと初期データを流す

Supabase の **SQL Editor** で、次の順に実行します。

| #   | ファイル                                           | 内容                                                                                      |
| --- | -------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 1   | `supabase/migrations/0001_init.sql`                | テーブル・RLS・`hybrid_search()`                                                          |
| 2   | `supabase/migrations/0002_signup_org_fallback.sql` | サインアップ時の所属解決・`assign_profile()`                                              |
| 3   | `supabase/migrations/0003_storage_policies.sql`    | Storage のRLS（**これが無いとアップロードが必ず失敗する**）                               |
| 4   | `supabase/migrations/0004_lexical_threshold.sql`   | pg_trgm のしきい値を日本語向けに下げる（**これが無いとキーワード検索が1件も発火しない**） |
| 5   | `supabase/migrations/0005_rate_limit.sql`          | 1日の質問回数の上限（**インターネットに公開するなら必須**。下の注記を読むこと）           |
| 6   | `supabase/seed.sql`                                | 組織「さくら総合病院」とメンバーの所属                                                    |

`seed.sql` は先にメールアドレスを書き換えてから実行します（次項）。

> **0002 を飛ばさないこと。** 0001 だけの状態だと、`org_id` を指定せずに
> 作られたユーザーでトリガーが not-null 違反を起こし、
> **ユーザー作成そのものが失敗します**。0002 はこれを
> 「アカウントは作られるが所属未設定」に変える修正です。

> **0005 は、ローカルで動かすだけなら要りません。**
> ただし Vercel などに公開するなら必須です。ログイン画面のデモボタンは
> `NEXT_PUBLIC_DEMO_PASSWORD` を使いますが、`NEXT_PUBLIC_*` は
> **ビルド時にクライアントのJSへ埋め込まれる**ため、公開した時点で
> パスワードは誰でも取り出せます。`/api/chat` は1回ごとに個人のAPIキーで
> Haiku・Embedding・Sonnet を叩くので、上限が無いと請求が青天井になります。
> 適用したら `npm run eval:quota` で効いていることを確かめてください。

## 2. ユーザーを3つ作る

**Authentication > Users > Add user** から作ります。Auto Confirm User を
オンにしておくとメール確認を省けます。

| メール（例）        | 表示名           | 部署     | 権限   | 用途                         |
| ------------------- | ---------------- | -------- | ------ | ---------------------------- |
| `admin@example.com` | 管理者           | 事務部   | admin  | 管理画面すべて               |
| `rt@example.com`    | 放射線科スタッフ | 放射線科 | member | 部署限定文書が**見える**側   |
| `nurse@example.com` | 看護部スタッフ   | 看護部   | member | 部署限定文書が**見えない**側 |

作った時点では所属未設定なので、この状態でログインすると
「プロフィールが未設定です。管理者にお問い合わせください。」と表示されます。
正常な挙動です。

`supabase/seed.sql` の3つの `assign_profile(...)` を、いま作った
メールアドレスに書き換えてから実行すると所属が入ります。
最後の `select` で3人が一覧に出れば成功です。

> 部署のチェックボックス（アップロード画面の「公開部署」）は
> **登録済みメンバーの部署から作られます**。先にユーザーを作っておかないと
> 選択肢が空になり、全社公開でしか登録できません。
> `医事課` も使いたい場合は、その部署のユーザーを1人足してください。

## 3. 文書6本を取り込む

`admin@example.com` でログインし、`/admin/documents` を開きます。

`demo/documents/` の6ファイルをまとめてドロップできますが、
**公開部署の設定が違うので2回に分けます**。

**1回目 — 全社公開（公開部署は何も選ばない）**

```
01_就業規則.md
02_旅費規程.md
03_育児介護休業規程.md
04_感染対策マニュアル.md
05_医療安全管理指針.md
```

**2回目 — 放射線科のみチェック**

```
06_放射線部門業務マニュアル.md
```

取り込みは1ファイルずつ直列に進みます（Embedding API のレート制限を
避けるため）。全部で 180 チャンク前後、数分かかります。
`status` が全て `ready` になれば完了です。

失敗した場合は一覧の「再取り込み」からやり直せます。
ファイル自体は Storage に上がっているので、再アップロードは不要です。

### 取り込めたかの確認

`/admin/documents/[id]/chunks` を開き、`01_就業規則.md` に

```
さくら総合病院 就業規則 > 第4章 休暇 > 第22条 年次有給休暇
```

という `heading_path` を持つチャンクがあることを確認します。
看板デモの質問「有給の繰り越しは何日まで？」はここに当てにいくので、
この階層が壊れていると台本が成立しません。

## 4. 部署フィルタが効いているか確認する

質問: **「造影剤の副作用が発生した場合、報告書はいつまでにどこへ提出しますか？」**（A-14）

### スクリプトで確認する

```bash
npm run eval:rls
```

3アカウントぶんのセッションを Admin API で発行し（パスワード不要）、
**実際のユーザーのJWTで** 文書一覧・検索・生成まで通して期待と突き合わせます。
期待どおりなら全員に ○ が付き、1件でもずれると終了コード 1 で落ちるので、
検索まわりを直したあとの回帰確認にも使えます。

```
○ 放射線科スタッフ  見える文書 6件  検索結果:混ざる    回答:する
○ 看護部スタッフ    見える文書 5件  検索結果:混ざらない 回答:拒否
○ 管理者            見える文書 6件  検索結果:混ざる    回答:する
```

### 画面で確認する（デモ動画の撮影用）

同じ質問を2アカウントで投げ分けます。

| ログインユーザー    | 期待する結果                             |
| ------------------- | ---------------------------------------- |
| `rt@example.com`    | 06_放射線部門業務マニュアル を出典に回答 |
| `nurse@example.com` | 「該当する記載が見つかりませんでした」   |

看護部側で回答が返ってきた場合は、`06` の公開部署設定が
放射線科のみになっているか（一覧の「公開部署」列）を確認してください。

### 効いている仕組みは2つある

看護部側の拒否は、**RLS だけで起きているのではありません**。順に働いています。

1. `hybrid_search()` が `security invoker` なので、RLS が **06 を検索結果に入る前に**落とす。
   画面側の条件分岐ではないので、アプリで絞り込みを書き忘れても漏れません。
2. 残った `05_医療安全管理指針` は cosine 閾値 0.35 を超えて生成まで進みますが、
   2段目の根拠判定が「この資料では答えられない」と拒否する。

つまり **1 だけでは拒否になりません**。デモで説明するときは、
「見せない」（アクセス制御）と「答えない」（根拠判定）が別の層にあることを
分けて話すと、実装の意図が伝わります。

## 5. 精度を測る

```bash
npm run eval
```

`demo/eval/questions.json` の30問を投げ、ベクトル検索のみと
ハイブリッド+RRF の Hit@1 / Hit@3 / Hit@5 / MRR を並べて出します。
生成は行わないので、費用は Embedding 30回分だけです。

**まず「キーワード側が1件以上ヒットした質問」の行を見ます。**
ここが 0 なら 0004 が未適用で、ハイブリッドを名乗っていても
中身はベクトル検索だけになっています。

続けて「答えられないときに答えない」が守れているかを測ります。

```bash
npm run eval:refusal
```

こちらは生成まで通すので $0.3 前後かかります。見るのは2つだけです。

- **誤答**（答えるべきでないのに答えた）… 0件であること
- **誤拒否**（答えるべきなのに拒否した）… 2件前後（B-01 と C-04。理由は README 参照）

答えが変な質問があったら、原因が検索か生成かを1問だけ見て切り分けます。

```bash
npm run inspect -- "有休っていつまで持ち越せる？"
```

欲しいチャンクが上位5件に入っていなければ検索の問題、
入っているのに使われていなければ生成の問題です。

これらのスクリプトは service role で実行するため **RLS が効きません**
（＝全文書が検索対象）。部署フィルタの検証は手順4の画面確認で行います。

## 6. 台本どおりに一周させる

`demo/README.md` の5分デモ台本を上から実行し、
④未回答キュー → ⑤FAQ登録 → ⑥即答 のループが回ることを確認します。

**本番のデモ前にリセットしておくこと**

```sql
-- ⑤で登録するFAQを消す（同じ質問が即答になったままだと⑥が見せられない）
delete from public.faq_overrides
where question like '%駐車場%';

-- 未回答キューを空にする（④で新規1件だけが見えるほうが分かりやすい）
delete from public.unanswered;

-- 会話ログを消す（管理画面のログを綺麗な状態から見せたい場合）
delete from public.conversations;
```

`conversations` を消すと `messages` / `citations` / `feedback` も
カスケードで消えます。`documents` と `chunks` は残るので取り込みのやり直しは不要です。

## つまずきやすいところ

| 症状                                                                 | 原因と対処                                                                                                                                                                                                                                          |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ユーザー作成が `violates not-null constraint` で失敗する             | `0002_signup_org_fallback.sql` が未適用。実行してからユーザーを作り直す                                                                                                                                                                             |
| ログインすると「プロフィールが未設定です」                           | `seed.sql` の `assign_profile` を、実際に作ったメールアドレスで実行する                                                                                                                                                                             |
| アップロード画面に公開部署の選択肢が出ない                           | メンバーがまだ居ない。部署は登録済みメンバーの `profiles.department` から作られる                                                                                                                                                                   |
| 取り込みが `failed` で止まる                                         | `OPENAI_API_KEY` の残高/レート制限をまず疑う。詳細は一覧の `error_message` に出る                                                                                                                                                                   |
| 何を聞いても「見つかりませんでした」                                 | 文書が `ready` になっていない、または `RAG_ANSWER_THRESHOLD` を上げすぎている（既定 0.35）                                                                                                                                                          |
| 逆に何でも答えてしまう（D問題で拒否できない）                        | **閾値を上げても直りません**（README「答えられないときに、答えない」参照）。`npm run eval:refusal` で誤答が出るなら、根拠判定が働いていない。`src/lib/answer.ts` の `SYSTEM_PROMPT` と、サーバーログの `[answer] 判定語が見つかりません` を確認する |
| `npm run eval` で「キーワード側が1件以上ヒットした質問: 0/27」と出る | `0004_lexical_threshold.sql` が未適用                                                                                                                                                                                                               |
| `npm run eval` が環境変数エラーで落ちる                              | `.env.local` に `SUPABASE_SERVICE_ROLE_KEY` が無い。`npm run eval` は `--env-file=.env.local` を前提にしている                                                                                                                                      |
| `.env.local` に書いてあるのに「未設定です」と言われる                | Node の `--env-file` は**シェルの環境変数を優先する**。`echo $ANTHROPIC_API_KEY` で空文字が入っていないか確認し、入っていれば `unset ANTHROPIC_API_KEY` してから実行する                                                                            |
